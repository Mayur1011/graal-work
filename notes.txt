notes related to testing scripts
using GenericDynamicCounters=true, so the runtime totals include all code executed from VM startup to shutdown—including DaCapo setup and teardown  [-Djdk.graal.GenericDynamicCounters=true]
GenericDynamicCounters=true counted runtime PEA activity from JVM startup until shutdown:
  - DaCapo harness startup
  - warm-up iterations
  - FOP execution
  - teardown/shutdown work

BenchmarkDynamicCounters=... clears the runtime counters at DaCapo’s starting marker and dumps at PASSED in. With -n 5, your pea-runtime.csv
  normally contains the final matched DaCapo iteration.



  The runner configures:

  -Djdk.graal.BenchmarkDynamicCounters=
      out,PEA-MEASUREMENT-START,PEA-MEASUREMENT-END

  Graal wraps System.out with a pattern-detecting stream.

  When it sees the start marker:

  1. It records the start time.
  2. It reads the current JVMCI counter array.
  3. It saves those values as the baseline.
  4. It begins the measurement.

  When it sees the end marker and the following newline:

  1. It reads the counter array again.
  2. It subtracts the baseline values.
  3. It writes only the interval delta to pea-runtime.csv.

  Thus, compilation and warmup executions before the marker do not enter the runtime result.

  The synchronous compilation options help ensure the methods are compiled before measurement:

  -XX:-TieredCompilation
  -XX:-BackgroundCompilation
  -XX:CompileThreshold=100




How do it get the pea-runtime.csv?
    Graal's existing BenchmarkCounters infrastructure writes it.
    in my running script i provide the destination: -Djdk.graal.BenchmarkCountersFile="$RESULTS_DIR/pea-runtime.csv"

  The full flow is:

  PEA instrumentation
      ↓
  DynamicCounterNode inserted into Graal IR
      ↓
  DynamicCounterNode lowered into machine-code counter increment
      ↓
  Generated application code executes
      ↓
  JVMCI counter slots are incremented
      ↓
  BenchmarkCounters reads the counter slots
      ↓
  BenchmarkCounters writes pea-runtime.csv

  Three kinds of DynamicCounterNode are inserted.

  ### Candidate executions

  Inserted by PEAEffectivenessReporter.recordCandidates():

  DynamicCounterNode.addCounterBefore(
      "PEA outcomes",
      "candidate executions",
      1,
      false,
      fixed
  );

  ### Initially virtualized

  Inserted by VirtualizerToolImpl.replaceWithVirtual():

  new DynamicCounterNode(
      "PEA outcomes",
      "initially virtualized",
      ConstantNode.forLong(1, graph),
      false
  );

  ### Final materialization

  Inserted during CommitAllocationNode lowering:

  DynamicCounterNode.addCounterBefore(
      "PEA outcomes",
      "final materialized",
      peaFinalMaterializedObjects,
      false,
      commit
  );

  At compilation time, DynamicCounterNode.generate() asks the backend to emit a benchmark-counter increment:

  lirGen.createBenchmarkCounter(...);

  Therefore, the counters become instructions in generated machine code.

  ### Measurement window

  The test prints:

  PEA-MEASUREMENT-START

  and later:

  PEA-MEASUREMENT-END

  The runner configures:

  -Djdk.graal.BenchmarkDynamicCounters="out,PEA-MEASUREMENT-START,PEA-MEASUREMENT-END"

  When BenchmarkCounters sees the start marker, it saves the current counters as a baseline.

  When it sees the end marker, it:

  1. Reads the current JVMCI counters.
  2. Subtracts the baseline.
  3. Writes the differences to pea-runtime.csv.

  So:

  pea-runtime.csv

  is written by:

  jdk.graal.compiler.hotspot.debug.BenchmarkCounters

  The runner only specifies the filename and later reads the file.

Use `dontinline` only on your classes/methods (and repeat for each class).

If your test class is `Test`:
```bash
-XX:CompileCommand=dontinline,Test.*
```

If you also have class `A`:
```bash
-XX:CompileCommand=dontinline,A.*
```

You can pass multiple:
```bash
-XX:CompileCommand=dontinline,Test.* \
-XX:CompileCommand=dontinline,A.*
```

This blocks inlining of those methods into callers, but other internal/JDK methods can still inline as usual.

## Important detail

If your test classes are in a package, use full class name pattern (package + class), e.g.:
```bash
-XX:CompileCommand=dontinline,my/package/Test.*
```
(or equivalent form accepted by your JVM build).

/*
In a compiler, an object's state is not a single, global tag.
The compiler tracks the state of the object at every specific point in the control flow graph.

looking at the Loop Header (BCI 10), it is a Merge Point where two distinct paths of the code join together.

The compiler looks at its storage/tracking info for the incoming paths:
1. Path A (outside): "Snapshot says b is VIRTUAL."
2. Path B (loop around): "Snapshot says b is MATERIALIZED."

the exact same object b.
The compiler knows it is the same object because it tracks its unique ID (e.g., virtual object with id 0).

But because the compiler traces timelines (execution paths), it arrives at the loop header with two conflicting timelines for that single object.
*/



ObjectState.java:
it does lazy allocation (CoW) of the object state. It only creates a new state when it detects a change in the object's status (e.g., from VIRTUAL to MATERIALIZED). If the object remains VIRTUAL, it continues to reference the same state, avoiding unnecessary duplication and saving memory.





---------------------------------------------
1. The shared framework
- EffectsPhase.java — the generic fixed-point driver. It schedules or builds a CFG, walks blocks with a closure, collects effects, applies them, runs DCE, and iterates until nothing changes.
- EffectsClosure.java — the analysis skeleton that stores aliases, per-block effects, loop merge effects, and applies the collected changes back to the graph in the right order.

- EffectList.java — the base list of deferred graph effects. It is the low-level container used to record edits before applying them.
- GraphEffectList.java — the concrete effect list for IR rewrites: add/delete nodes, replace values, update virtual mappings, kill branches, and track how many allocations/virtualizations changed.
- EffectsBlockState.java — the common per-block state base class. It tracks whether a path is dead and which exception edges should be killed, and provides map-comparison helpers.

2. Partial escape analysis itself
- ObjectState.java — the state of one virtual object while analysis runs: its field/array entries, lock stack, whether it must stay virtual, and the materialized value if it escapes.
- PartialEscapeBlockState.java — the per-basic-block state for PEA. It stores all ObjectStates indexed by virtual-object id and supports copy-on-write for efficiency.
- PartialEscapeClosure.java — the core PEA traversal logic. It is the class that visits nodes, virtualizes allocations, materializes objects when needed, handles merges/loops, and records the effects. It also contains the Final specialization.
- PartialEscapePhase.java — the phase entry point for running PEA. It controls iteration count, optional early read elimination, cleanup, graph-state staging, and which closure implementation to create.
- FinalPartialEscapePhase.java — the “final” wrapper around PartialEscapePhase, used for the last PEA pass and to mark the FINAL_PARTIAL_ESCAPE stage in graph state.
- VirtualizerToolImpl.java — the concrete implementation of VirtualizerTool. It is the bridge from node virtualization requests back into PartialEscapeBlockState and graph-effect recording.
- VirtualUtil.java — helper utilities for PEA/read-elimination: graph matching, tracing, and the “assert obsolete nodes are really unreachable” debug check

graal PEA is compile-time, IR-based, control-flow-sensitive static analysis performed by the JIT compiler.
graal is a jit compiler, so this analysis happens when the code in running, but it does not make it dynamic analysis.
compiltion itself is dynamic, but PEA is static.
