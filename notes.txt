STEPS:

ON LOCAL MACHINE:
1. Clone the graal repository in your local machine
  - git clone https://github.com/oracle/graal.git
  - Make graal_IR, graal_programs, mx-cache directories in the same location as graal/

1. To build the docker image and run the container, use the following commands:
  - docker build -t graal-dev:latest .
  - docker run -it --rm -v /path/to/graal-dev:/graal-dev graal-dev:latest bash

1. If we are using compose, we can use the following command to run the container:
  - docker compose up -d --build
  - docker compose up -d
  - docker compose exec graal bash

2. Select the JDK with JVMCI support using mx fetch-jdk
  - mx -y fetch-jdk default
  - export JAVA_HOME=/home/ubuntu/.mx/jdks/labsjdk-ce-latest-jvmci-25.1-b17_amd64
  - export PATH=$JAVA_HOME/bin:$PATH

3. Build the compiler using mx build
  - cd graal/compiler
  - mx java -version
  - mx build

/*
In a compiler, an object's state is not a single, global tag.
The compiler tracks the state of the object at every specific point in the control flow graph.

looking at the Loop Header (BCI 10), it is a Merge Point where two distinct paths of the code join together.

The compiler looks at its storage/tracking info for the incoming paths:
1. Path A (outside): "Snapshot says b is VIRTUAL."
2. Path B (loop around): "Snapshot says b is MATERIALIZED."

the exact same object b.
The compiler knows it is the same object because it tracks its unique ID (e.g., virtual object with id 0).

But because the compiler traces timelines (execution paths), it arrives at the loop header with two conflicting timelines for that single object.
*/



ObjectState.java:
it does lazy allocation (CoW) of the object state. It only creates a new state when it detects a change in the object's status (e.g., from VIRTUAL to MATERIALIZED). If the object remains VIRTUAL, it continues to reference the same state, avoiding unnecessary duplication and saving memory.





---------------------------------------------
1. The shared framework
- EffectsPhase.java — the generic fixed-point driver. It schedules or builds a CFG, walks blocks with a closure, collects effects, applies them, runs DCE, and iterates until nothing changes.
- EffectsClosure.java — the analysis skeleton that stores aliases, per-block effects, loop merge effects, and applies the collected changes back to the graph in the right order.

- EffectList.java — the base list of deferred graph effects. It is the low-level container used to record edits before applying them.
- GraphEffectList.java — the concrete effect list for IR rewrites: add/delete nodes, replace values, update virtual mappings, kill branches, and track how many allocations/virtualizations changed.
- EffectsBlockState.java — the common per-block state base class. It tracks whether a path is dead and which exception edges should be killed, and provides map-comparison helpers.

2. Partial escape analysis itself
- ObjectState.java — the state of one virtual object while analysis runs: its field/array entries, lock stack, whether it must stay virtual, and the materialized value if it escapes.
- PartialEscapeBlockState.java — the per-basic-block state for PEA. It stores all ObjectStates indexed by virtual-object id and supports copy-on-write for efficiency.
- PartialEscapeClosure.java — the core PEA traversal logic. It is the class that visits nodes, virtualizes allocations, materializes objects when needed, handles merges/loops, and records the effects. It also contains the Final specialization.
- PartialEscapePhase.java — the phase entry point for running PEA. It controls iteration count, optional early read elimination, cleanup, graph-state staging, and which closure implementation to create.
- FinalPartialEscapePhase.java — the “final” wrapper around PartialEscapePhase, used for the last PEA pass and to mark the FINAL_PARTIAL_ESCAPE stage in graph state.
- VirtualizerToolImpl.java — the concrete implementation of VirtualizerTool. It is the bridge from node virtualization requests back into PartialEscapeBlockState and graph-effect recording.
- VirtualUtil.java — helper utilities for PEA/read-elimination: graph matching, tracing, and the “assert obsolete nodes are really unreachable” debug check
