  1. It records the start time.
  2. It reads the current JVMCI counter array.
  3. It saves those values as the baseline.
  4. It begins the measurement.

  1. It reads the counter array again.
  2. It subtracts the baseline values.
  3. It writes only the interval delta to pea-runtime.csv.

## Assessment of the three questions

Question: Compile-time virtualized/materialized objects
Current status : Partial
What is actually measured: Unique source allocation sites and cumulative compilation/inlining-context outcomes—not runtime objects and not exact IR occurrence counts

Runtime virtualized/materialized objects
Strong, with scope limitations
Executions of instrumented PEA candidates while Graal-compiled machine code runs

Reason for each materialization
Strong for M, incomplete for all heap allocations
Every tracked virtualized-then-materialized occurrence receives one materialization-trigger category


Compile-time finalization:
currently: for each alloc site reached to pea, outcomes seen across compilation and inling context






 One important limitation is that a static context is keyed by site, compilation and
  inline chain. Multiple allocation-node copies with the same source position inside
  one context can collapse into one record in graal/compiler/src/jdk.graal.compiler/
  src/jdk/graal/compiler/virtual/phases/ea/PEAEffectivenessReporter.java:312. If one
  copy scalar-replaces and another materializes, the current Boolean state can lose
  that distinction.

  The optional compiler CounterKey values are not a complete solution. The
  virtualization counter is incremented when virtualization is requested during
  analysis, while materialization is counted much later during surviving commit
  lowering. They therefore do not represent symmetric final IR outcomes.

  For publication, choose one of these formulations:

  - Preferred: “compile-time allocation-site outcomes.”
  - Additional metric: “final IR allocation occurrences per compilation context.”
  - Avoid: “compile-time object count.”

  If you require exact IR occurrence counts, an occurrence identity must be
  propagated from the original allocation node through its virtual and materialized
  forms.

One thing to be aware of (not a bug, but a common source of confusion when interpreting results): "Static sites observed" (111) is far smaller than "PEA-eligible sites" (1874) — that's expected, since only allocation sites in code that actually got JIT-compiled and reached PEA show up as observed candidates; the rest are cold and never went through PEA. And "Compile-time reason: X" counts are raw IR occurrence counts across all compilations (not deduplicated per site), so they won't line up 1:1 with the site-level always_materialized/mixed counts — different units, both correct, just don't cross-compare them directly.

What actually needs to be built

This is the important caveat: Graal already inlines aggressively before PEA runs (inlining is a separate earlier phase; PartialEscapePhase requires unlessRunBefore(HIGH_TIER_LOWERING), i.e., it runs late, after inlining decisions are made). So SMC/SMI in Graal terms mostly reduces to "make the existing profile-guided devirtualization/inlining heuristics aware that an argument is a to-be-virtualized allocation, and bias them toward inlining/devirtualizing it" — not a new speculation engine. That's a small, targeted change (a hint from VirtualizerToolImpl back to the inlining phase), not new infrastructure.

SBE is the real gap and the real payoff here. It needs:

1. A speculation point at merges. In PartialEscapeClosure's merge-processing (EffectsClosure.java merge handling → the calls around line 1400-1930), when two branch states disagree on a virtual object, instead of unconditionally materializing on both incoming edges, check the IfNode's branch probability (already available via ProfileData/BranchProbabilityNode info Graal tracks everywhere). If one edge is cold (say <5%), keep the object virtual along the hot edge and insert a deopt guard on the cold edge carrying the object's virtual state in the FrameState (Graal's deopt machinery already reconstructs materialized objects from virtual-object descriptors in a FrameState for the "deopt while still virtual" case — that's the "dynamic heapification" the paper describes, and it already exists for ordinary uncommon traps).
2. A PEAMaterializationReason for the speculative path, e.g. SPECULATIVE_BRANCH_MATERIALIZED, distinct from merge_incompatible, so your reporter can measure how often the speculation actually pays off vs. how often the guard fires (deopt rate) — you need that number to know if this is a net win, since a bad guess costs a full deopt.
3. A correctness constraint: only legal when the cold-edge materialization would be a pure side-effect-free heapify (no observable effects have run since the branch that can't be undone by a deopt). Graal's deopt framework already enforces this for FrameState-based rematerialization, so this constrains you to speculating at points where you're already inside a deoptimizable region — should hold for ordinary hot loops in sunflow.

Recommendation

Don't build SMC/SMI as new machinery — check whether inlining decisions already account for PEA candidates, and if not, feed a "this callee receives a virtualizable allocation" signal into the existing inlining cost model (cheap, call_argument/method_return are only 4% of your cost anyway).

Build SBE as the actual research contribution: one guarded/speculative merge path in PartialEscapeClosure, gated by branch probability, with a new reason id to measure hit/miss rate. That's the 89%-of-cost lever, and it's the part of the paper Graal doesn't already do.

ObjectState.java:
it does lazy allocation (CoW) of the object state. It only creates a new state when it detects a change in the object's status (e.g., from VIRTUAL to MATERIALIZED). If the object remains VIRTUAL, it continues to reference the same state, avoiding unnecessary duplication and saving memory.





---------------------------------------------
1. The shared framework
- EffectsPhase.java — the generic fixed-point driver. It schedules or builds a CFG, walks blocks with a closure, collects effects, applies them, runs DCE, and iterates until nothing changes.
- EffectsClosure.java — the analysis skeleton that stores aliases, per-block effects, loop merge effects, and applies the collected changes back to the graph in the right order.

- EffectList.java — the base list of deferred graph effects. It is the low-level container used to record edits before applying them.
- GraphEffectList.java — the concrete effect list for IR rewrites: add/delete nodes, replace values, update virtual mappings, kill branches, and track how many allocations/virtualizations changed.
- EffectsBlockState.java — the common per-block state base class. It tracks whether a path is dead and which exception edges should be killed, and provides map-comparison helpers.

2. Partial escape analysis itself
- ObjectState.java — the state of one virtual object while analysis runs: its field/array entries, lock stack, whether it must stay virtual, and the materialized value if it escapes.
- PartialEscapeBlockState.java — the per-basic-block state for PEA. It stores all ObjectStates indexed by virtual-object id and supports copy-on-write for efficiency.
- PartialEscapeClosure.java — the core PEA traversal logic. It is the class that visits nodes, virtualizes allocations, materializes objects when needed, handles merges/loops, and records the effects. It also contains the Final specialization.
- PartialEscapePhase.java — the phase entry point for running PEA. It controls iteration count, optional early read elimination, cleanup, graph-state staging, and which closure implementation to create.
- FinalPartialEscapePhase.java — the “final” wrapper around PartialEscapePhase, used for the last PEA pass and to mark the FINAL_PARTIAL_ESCAPE stage in graph state.
- VirtualizerToolImpl.java — the concrete implementation of VirtualizerTool. It is the bridge from node virtualization requests back into PartialEscapeBlockState and graph-effect recording.
- VirtualUtil.java — helper utilities for PEA/read-elimination: graph matching, tracing, and the “assert obsolete nodes are really unreachable” debug check
